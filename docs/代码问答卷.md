# 代码问答卷提纲（20 问）

> 用途：应对验收的「代码问答卷」与抽查面谈。每题给出**答案要点 + 代码位置**，回答时能指着文件讲。
> 说明：题库按本项目**真实实现**编写，不含未实现的功能。

---

## A. 架构与线程（4 题）

**1. 你用的是 Java，课程要求「协程 + ViewModel」，你怎么对应？**
- Java 没有协程，等价方案是 **ViewModel + LiveData + ExecutorService**：
  `util/AppExecutors.java` 里 `diskIO` 单线程（保证数据库写入顺序）、`networkIO` 三线程（并发抓取）、`main()` 用 Handler 切回主线程。
- 「协程的取消」在这里对应为 LiveData 的观察者随生命周期自动解绑；不会出现 Activity 销毁后回调更新 UI 的崩溃。

**2. 为什么 ViewModel 不持有 Activity/Fragment？**
- 屏幕旋转时 Activity 重建、ViewModel 存活；持有 View 会泄漏旧 Activity。
- 本项目里 ViewModel 只暴露 `LiveData` 与动作方法，例如 `FeedsViewModel.refreshAll()`，不 import 任何 `android.view.*`。

**3. Room 的 LiveData 查询为什么能自动刷新？**
- Room 在编译期生成 `InvalidationTracker` 的观察代码，表数据变化时自动重新执行查询并发射新结果。
- 所以「刷新完成后列表自动更新」不需要手动 notify，见 `ArticleDao.observeAll()` 的用法。

**4. 主线程有没有做过 I/O？怎么保证？**
- 没有。所有数据库与网络操作都在 `AppExecutors` 的线程池里；Room 的 `LiveData` 查询自带异步。
- 唯一在主线程做的是**纯内存排序**（`ArticleRepository.rank()`，n 为本地文章数，几百条、无 I/O），代码里写了注释说明理由。

## B. 解析与网络（5 题）

**5. RSS 2.0 和 Atom 有什么区别？你怎么用一套代码兼容？**
- 链接：RSS 是 `<link>文本</link>`，Atom 是 `<link rel="alternate" href="..."/>`；正文：RSS 用 `<description>`，Atom 用 `<content>`。
- 判据是「`<link>` 有没有 `href` 属性」，见 `RssParser` 的 `START_TAG` 分支。

**6. 为什么用 XmlPullParser 而不是 DOM？**
- 流式解析，内存占用与文档大小无关（IT之家一次 60 条、272 KB）；DOM 要整棵树建完。
- 它还是 Android 内置的，不引第三方 XML 库。

**7. 源是 GBK 编码怎么办？**
- `parser.setInput(inputStream, null)`，第二参数传 null 让解析器按 BOM 与 `<?xml encoding?>` 自行判定，不要硬编码 UTF-8。

**8. 文章去重在哪一层做的？为什么不在解析层做？**
- 解析层只管把文档读成对象；去重在仓库层 `FeedRepository.toEntities()`（同一次抓取内按 link 去重）+ 数据库唯一索引（跨次去重）。
- 两层配合：内存去重减少无效插入，唯一索引兜底并发。

**9. 抓取失败时，界面拿到的是什么？**
- 不是原始异常，而是 `NetworkErrorMapper` 翻译后的中文（如「网络不可用：无法解析服务器地址」）。
- 它沿 cause 链匹配 `UnknownHostException / SocketTimeoutException / SSLException / XmlPullParserException`，避免把英文堆栈抛给用户。

## C. 数据与算法（4 题）

**10. 未读数是每条源查一次数据库吗？**
- 不是。`FeedDao.observeAllWithUnread()` 用 SQL 子查询一次算完：
  `SELECT f.*, (SELECT COUNT(*) FROM articles a WHERE a.feedId = f.id AND a.read = 0) AS unreadCount FROM feeds f`。
- 避免 N+1 查询。

**11. 为什么添加订阅要用事务？**
- 要同时插 1 条 feed 和多条 articles。若中途失败会留下「有源没文章」的脏数据；`database.runInTransaction()` 保证整体成功或整体回滚。

**12. 你的推荐算法为什么这么设计？**
- `raw = 1 + 3×收藏 + 1×未读 + 2×health`，`score = raw / (ageHours/6 + 1)^1.2`。
- 前三项让「用户在意」的文章靠前，时间项让新文章有机会；指数 1.2 控制衰减速度，6 小时是半衰参考尺。
- 写成纯函数 `ArticleRanker.score()`，可以直接单测断言数值关系（6 个用例）。

**13. 健康度怎么影响排序？失败退避呢？**
- `FeedHealth.healthScore()`：0 次失败 = 1.0，1 次 = 0.67，达到阈值 3 次 = 0，所以在推荐流里自然降权。
- 退避：失败 1/2/3/≥4 次分别等 10 分钟 / 1 小时 / 6 小时 / 24 小时，后台刷新时跳过未到期的源（`canFetchNow`）。

## D. 后台与权限（3 题）

**14. WorkManager 和 Service 有什么区别？你为什么用它？**
- Service 要自己管生命周期、在 Doze 下会被杀；WorkManager 由系统调度，支持约束（联网）、重试退避、唯一任务名。
- 本项目 `RefreshScheduler` 用 `enqueueUniquePeriodicWork(..., UPDATE, ...)`，重复调用不会产生多个并行任务。

**15. 用户拒绝通知权限后，你的 App 怎么表现？**
- 刷新、阅读、备份全部照常；`NotificationHelper.canNotify()` 返回 false 就不发通知。
- 设置页如实显示「已拒绝通知权限。功能仍可正常使用」，并给重新授权按钮。
- `notify()` 外层还 catch 了 `SecurityException`，防止权限在调用瞬间被撤销导致 Worker 整体失败。

**16. 怎么确认后台任务真的在执行？**
- 不信「代码看起来对」：`dumpsys jobscheduler` 看 job 是否存在、`cmd jobscheduler run -f` 强制触发后看 `RefreshWorker` 日志。
- 正是这样发现过一次 `androidx.work.workdb` 被写坏成 0 字节、任务静默不执行的问题，之后在设置页加了「后台任务状态」显示。

## E. UI 与兼容（2 题）

**17. Android 15 上界面被状态栏压住，你怎么修的？**
- targetSdk 35 在 Android 15 强制 edge-to-edge，内容会顶到状态栏下。
- 用 `ViewCompat.setOnApplyWindowInsetsListener` 按 `systemBars()` 的 insets 给根布局加 padding；`fitsSystemWindows` 在这种强制模式下不生效。

**18. 加载 / 空 / 错误三态怎么统一的？**
- 抽成自定义控件 `StateView`（`showLoading / showEmpty / showError / hide`），列表页两行代码接入。
- 列表已有内容时错误用 Snackbar + 重试，不盖住内容；列表为空时才铺满错误页。

## F. 伴生模块（2 题）

**19. 备份为什么不直接拷 .db 文件？**
- SQLite 在 WAL 模式下，主文件可能不含最新事务，拷出来是**不一致的快照**。
- 所以走 DAO 读全量 → 序列化成 JSON：快照一致、可读、可跨版本迁移（带 `schemaVersion`）。

**20. 重复导入同一份备份会怎样？**
- 订阅源按 `url` 去重，已存在就复用本机 id；文章按 `link` 去重，已存在时按用户选择「覆盖阅读/收藏状态」或「保留现有状态」。
- 因此重复导入不会产生重复数据，只会更新状态；整个恢复在一个事务里完成。

## 附：最可能被追问的三处「真话」

1. **「这行代码为什么这么写」** → 指到具体文件与方法，讲清输入输出，不背概念。
2. **「这个 bug 你怎么发现的」** → 用真实经历答：状态栏遮挡是看截图发现的、workdb 是强制触发没日志查出来的、构建缓存损坏是异常断电后报 `Invalid classfile header`。
3. **「哪些是 AI 帮你写的」** → 如实说：AI 参与实现与文档整理，但每个模块的线程模型、去重策略、事务边界、权限降级都能当场讲清并现场改。
